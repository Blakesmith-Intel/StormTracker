# V9.15.0 candidate — always-on measured tracks and observed-intensity preservation

Defect priority: P1 — user-observed false-low visual intensity.
Source: user 8.27-second phone capture IMG_8644.mp4 (8 October 2026).

## Reproduction and cause

The supplied video shows a visibly weaker blue/purple storm when
"Track-specific 3-D" is enabled, while disabling the checkbox reveals
a stronger, broader green/yellow/red-looking storm, without a corresponding
frame/time change that would justify a real storm intensification.

The old mode toggle selected **two different spatial and display paths**:
- OFF: frame-wide inferred 3-D from every available 2-D reflectivity pixel.
- ON: inferred vertical columns restricted to worker-segmented tracked cells.

In ON mode, the visible points were coloured only from **inferred dBZ at
each height**, rather than retaining the measured reflectivity colour
of the tracked cell's original 2-D footprint. The frame-wide view also
included untracked pixels. Those facts can legitimately differ, but the
UI made it look like the **same observed storm** became weaker by choosing
tracking, which is unacceptable in an operational situational-awareness map.

The previous V9.15 candidate also applied the same *display* threshold
for both modes, but this by itself did not preserve measured intensity.

## Implemented repair

1. Remove the "Track-specific 3-D" OFF checkbox. A read-only label now
   states "Track-specific 3-D · always on".
2. For every observed scan with measured track volumes, draw tracked
   volumes by default. Do not promote temporally interpolated frames to
   measured tracks. If there is no measured track, use the existing
   explicitly labelled frame-wide inference fallback.
3. Preserve the raw **BoM 2-D reflectivity palette category** of every
   pixel inside the measured track segmentation in a separate
   `measured_reflectivity_footprint` array. Capture it even where
   `inferColumn` yields no vertical profile.
4. Draw that *measured 2-D reflectivity footprint as a clearly labelled
   projection at the base of the tracked storm*, using precisely
   `SOURCE_PALETTES.reflectivityRgb` (`displayRgb`) rather than the
   predicted at-altitude `point.dbzh`. Use the same user-visible dBZ
   cutoff for the projected measured base and inferred dots.
5. Continue drawing inferred points at their inferred vertical altitudes
   with `colourForDbzh(point.dbzh)` and their original confidence opacity.
   **Do not** paint all vertical heights as if the low-level radar dBZ were
   directly measured at every altitude.
6. Invalidate the static HTML/JS module caches so previous toggling
   behaviour cannot persist across GitHub Pages reloads.

## Science and caveats

BoM radar reflectivity is measured as *reflectivity categories / dBZ*,
not direct rain-rate measurements in mm/h. The projected measured-echo
layer preserves the **source reflectivity intensity and colour**, not
a guaranteed physical rain rate or a measured echo altitude.
Track segmentation still correctly restricts tracked volumes to observed
storm-cell footprints; it does not create measured tracks for untracked
echoes or temporal gap-fill frames. The measured radar imagery remains
independently draped on the map with the user's selected opacity.

The model calibration, vertical profile inference, Doppler science,
measured storm segmentation, track IDs, 40 dBZ tops, confidence/support,
trends and history have not been modified.

## Test and release gates

- Existing full frontend regressions must pass.
- New always-on tests reject the old checkbox and verify source
  reflectivity category preservation and inferred-height separation.
- Source-pixel synthetic volume tests verify preservation of the 2-D
  footprint without changing the track 3-D metrics.
- Desktop/mobile browser QA required under active observed storms,
  comparing original 2-D BoM category colours and the projected track
  intensity at the same timestamp and location.
- Performance QA needed with dense storm coverage due the additional
  measured-base point per tracked 2-D radar cell.
- Production remains untouched until approval and the accepted baseline
  and restore path are preserved.
