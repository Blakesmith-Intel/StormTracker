# StormTracker V9.18 — BoM radar history source recovery review
**13 October 2026 · isolated browser-only experiment · no production changes**

## Confirmed fault from DevTools
The supplied initial-load capture recorded 35 separate HTTP 400 WMTS requests against the same BoM reflectivity tile at differing guessed five-minute `time` values. This is `discoverBomReflectivityHistory` scanning the requested 180-minute window plus 60-minute publication allowance (up to 48 candidate guesses), irrespective of whether radar playback is paused. Concurrency/duplicate-URL controls could not suppress *different* rejected URLs.

Two river-history 502s and Cesium outline warnings in the same capture are separate faults. They do not establish a GPU crash cause, and the absence of WebGL errors in one truncated capture does not prove those errors resolved.

## Existing correction
Development main had already gained `discoverBoundedBomReflectivityHistory`, with tests limiting first discovery to four failed timestamp probes and a limited rolling live set. The `/preview/label-gpu-guard/` route uses that bounded initial lookup; **the sealed production root does not**. Bounded discovery still makes guesses, not official published-timestamp metadata queries.

## New isolated preview
`https://blakesmith-intel.github.io/StormTracker/preview/radar-history-fix/`

Inherits the full current label/GPU experimental build, the no-fabrication relay pressure guard, all radar and Doppler imagery, 3-D volume, terrain, labels, floods, outages and multi-radar options. Compared with `/preview/label-gpu-guard/`, the following changes are path guarded:

- Both cold/interactive history discovery and automatic new-frame checks use bounded BoM candidate discovery (at most four failed recent probes on a source outage). No 48-timestamp startup flood. This does **not** invent or silently synthesize frames.
- Initial source-discovery failure may use **only authentic BoM frames already persisted in the browser**. Distinguish those clearly from live feeds. A cold start with no cached authentic source data reports that no imagery is available, rather than looping endlessly.
- Automatic new-frame discovery failures preserve the last displayed, genuine BoM frame and its timestamp, without clearing the scene or implying updated data.
- The existing network guard keeps the WMTS concurrency limit and cool-down from denial/outages; cache warming stops on relay refusal. 
- The site runs entirely in browser + current static GitHub Pages and existing Cloudflare relay. No new hosting or paid infrastructure.

## Important unresolved point: authoritative time metadata
The current relay's `/wmts` route requires a whitelisted `LAYER` for every request and forwards only selected WMTS GetTile query parameters. A bare `GetCapabilities` request is rejected. Without a verified, exposed BoM WMTS time-dimension or similar authoritative manifest, we **cannot truthfully claim this test eliminates all invalid timestamp probes**. At most four failures can still appear when the live source is unavailable.

A future definitive fix can read the BoM time dimension from an authenticated, allowed and properly CORS-handled WMTS capabilities/metadata path, but first verify the actual upstream response and schema and the relay deployment permissions. Do not introduce a new Cloudflare Worker, hidden remote source, heuristic fake scan or deployment to the live relay without reviewing its effect.
